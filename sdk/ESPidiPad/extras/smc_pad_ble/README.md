# Кит SMC-PAD Pro по BLE: протокол в обе стороны

Для Даниила и его агента: как стоковый M-VAVE SMC-PAD Pro общается по Bluetooth LE. С этим ESP32 (ESPidi,
`sdk/ESPidiPad`, NimBLE central) может читать контролы пэда и управлять его подсветкой, **не меняя прошивку пэда**.

## Что внутри

| файл | что это |
|---|---|
| `PROTOCOL.md` | спецификация (на английском): GATT, что пэд шлёт (BLE-MIDI и как его кнопки, энкодеры и пэды превращаются в сообщения), что пэду можно слать (протокол настройки на `AE40`), рецепты, правила для хоста. У каждого факта пометка происхождения |
| `ref/smc_pad_protocol.py` | эталонная реализация на Python: сборка и разбор пакетов, сборщик ответов из уведомлений, разбор BLE-MIDI, раскладка профиля, защита от опасных команд |
| `ref/test_smc_pad_protocol.py` | 18 тестов, в том числе на байтах, снятых с настоящих пэдов: последовательность подключения совпадает с захваченной сессией байт в байт |
| `esp32/SmcPadProtocol.h` | то же на C++11 для ESP32: без STL, исключений, кучи и BLE-стека; годится для Arduino-ESP32 и ESP-IDF |
| `esp32/test/` | проверка заголовка на хосте по векторам Python-эталона |
| `vectors.json` | тестовые векторы для любой реализации (генерируются `ref/make_vectors.py`) |
| `AGENTS.md`, `CLAUDE.md` | правила для агента |
| `OPEN_QUESTIONS.md` | что ещё не проверено на устройстве и как проверить |
| `NOTICE.md` | авторство, источники, атрибуция |

## Коротко о протоколе

- **Пэд → хост.** Нажатия, энкодеры и кнопки приходят обычным BLE-MIDI (сервис `03B80E5A…`, характеристика
  `7772E5DB…`, notify). Что именно шлёт каждый контрол, задаётся записью в активном профиле. Её можно прочитать
  и разобрать (раздел 2 спецификации).
- **Хост → пэд.** Настройки и цвета светодиодов идут через сервис `AE40`. Пакеты `00 59 <cmd> <len24> <data>
  <checksum>` пишутся в `AE41` (только write without response), ответы приходят уведомлениями `AE42`. Цвет пэда —
  запись трёх байт в RAM пэда, применяется сразу, флеш не изнашивает (раздел 4). Обычные ноты и CC подсветку
  не включают.
- **Главные правила:** один запрос в полёте, таймаут на ответ; пэд сам не проверяет границы и молча отбрасывает
  лишнее. Несколько команд опасны (запись во флеш, калибровка, перезагрузка в загрузчик), и сборщики их не
  пропускают.

## Как начать

```
cd ref && python -m unittest -v test_smc_pad_protocol
cd ../esp32/test && c++ -std=c++11 -Wall -Wextra -I.. test_protocol.cpp -o test_protocol && ./test_protocol
```

Дальше со стороны ESP32: подключиться к пэду (первый раз — в режиме сопряжения), подписаться на `AE42` и на
BLE-MIDI, прочитать идентификатор, регион 4 и регион 5, затем разбирать BLE-MIDI по прочитанным записям и
писать цвета `color_write()`.

## Статус

- Протокол со стороны прошивки пэда разобран по полному дампу (идентификатор `SMC-PAD_004`). Со стороны
  приложения и захватов он сверен с работой spectalive/smc-pad.
- На устройстве в этом ките ничего не проверялось. Результаты стенда Руслана по `OPEN_QUESTIONS.md` придут
  обновлением, в первую очередь ответ, можно ли пропустить 28 КиБ чтения при подключении.
- Если у твоего пэда другой идентификатор (не `SMC-PAD_004`), сообщи: детали могут отличаться.
